# Initial STRIDE threat model

## Overview

Scope: the Phase 0 repository foundation, reviewed 2026-09-14. This is an architecture threat model, not a completed vulnerability audit. An independent read-only architecture review was reconciled with source and local test results. Owner-supplied product requirements describe intended future behavior; source evidence below describes the implemented baseline.

Implementation verification includes real signed-token rejection tests and a regression for unsupported `Accept` headers: the exception boundary falls back to a fixed JSON Problem Details response rather than allowing Development's exception page. Host lifecycle and dependency tests do not establish tenant isolation or external-service readiness.

The Angular shell renders static text; API routes are anonymous liveness, host readiness and fixed Problem Details; the worker only handles lifecycle. PostgreSQL/RabbitMQ are optional Compose services with no application clients. Object storage, memberships, incidents, evidence, audit and notifications have no runtime implementation. See the [trust-boundary DFD](data-flow.md) and [C4 views](../../docs/architecture/README.md).

## Threat Model, Trust Boundaries, and Assumptions

Present assets are source/configuration integrity, local development credentials and disposable volumes, diagnostic data and authentication policy. Future assets are tenant incidents, evidence bytes/hashes, membership/role integrity, browser tokens and audit history. Actors are unauthenticated HTTP callers, future authenticated members of another tenant, local processes, trusted developers/Docker administrators, external identity and telemetry operators, and dependency/PR contributors.

Clients control requests, headers and their own browser; they do not gain authority from IDs or tokens that fail validation. Local processes can reach loopback services. Host/Docker administrators already control local data and are not isolated by Compose. Trusted operator configuration selects OIDC/OTLP endpoints; request parameters do not. Builds consume external packages as a supply-chain boundary.

Existing controls: explicit anonymous diagnostic allowlist; fail-closed default identity; exact `(iss, sub)` key; signed JWT issuer/audience/lifetime/RS256 checks and scope policy; fixed safe errors; correlation without using it as identity; loopback services; ignored local env/state; package/provider locks and compiler checks. Membership/tenant queries, RLS, presigned operations, audit persistence, encryption at rest and consumer reliability are planned, not proven.

The incoming W3C trace context may influence trace IDs. The separate X-Correlation-ID request header is ignored; neither field is trusted for authorization. `AllowedHosts` is not listener binding. Readiness measures host lifecycle only. Public diagnostics have no rate limiter in Phase 0; use only a local synthetic-data environment. Tests use ephemeral RSA/static metadata and verify no live discovery or PKCE flow.

Accepted scope limits from owner instructions: no AWS resources/authentication in Phase 0, no real sensitive data, and deferred local object storage after rejecting archived MinIO. No unsupported-dependency exception was accepted. Local HTTP/no TLS and missing product controls are development limitations, not accepted production risks. Before exposing a deployment, review residual risks explicitly.

## Severity Calibration (Critical, High, Medium, Low)

Critical would require demonstrated broad production compromise, such as unauthenticated access to all tenants or execution in a privileged deployment identity; neither surface exists here. High examples are cross-tenant evidence access or a real auth bypass once data endpoints exist. Medium includes reachable service exhaustion or exposure of bounded local development data. Low includes diagnostic metadata without sensitive content or authority. A local administrator reading a Docker volume they already control is not a new privilege gain. Missing future features are roadmap items, not confirmed current vulnerabilities; confidence in unimplemented/live-provider controls remains explicitly unknown.
